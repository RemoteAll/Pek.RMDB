## 3. 架构与依赖审计

### 3.1 模块划分

| 模块 | 职责 | 线程/锁 |
|---|---|---|
| `value` | 值枚举、规范化、时间解析、JSON 文本 | 无状态 |
| `model` | `CacheObject` 契约、字段/约束描述、结果结构 | 无状态 |
| `index` | 类型感知索引；ID 集合 `BTreeSet<i64>` | 由表写锁保护；查询计数 `AtomicU64` |
| `unique` | 单/复合唯一索引；两阶段原子写入 | 由表写锁保护 |
| `table` | 单表状态（主存储 + 索引 + 唯一 + ID 计数 + 脏标记） | `RwLock<State>`；`Mutex` 串行化写盘 |
| `json` | 实体序列化/反序列化（C# `SimpleJsonString` 契约）；通用宽松解析/转义复用 `dhrust::json` | 无状态 |
| `persistence` | 原子写、写合并调度 | `Mutex + Condvar`（1 线程） |
| `db` | 门面、表注册、后台线程、统计 | `RwLock<HashMap>`（表注册） |

依赖：`chrono`（时间类型）+ `dhrust`（`times::parse_datetime`、`json::{JsonValue, parse_lax, write_quoted}`、`io::safe_replace_file`）；无 serde、无异步运行时、无第三方数据结构库。

### 3.2 并发模型与锁序

- **读路径**：`RwLock` 读锁 → `HashMap` 查找 → `Arc<T>` 克隆（原子递增）→ 释放。多读并发无阻塞。
- **写路径**：`RwLock` 写锁内完成「唯一校验 → ID 分配 → 普通索引 → 唯一索引 → 主存储」；无嵌套锁。
- **持久化**：后台线程读锁收集脏表快照（克隆 `Arc` 列表）→ 释放读锁 → 序列化 → 每表 `Mutex` 内原子写。
  - 锁序固定：`表 RwLock` → `表 save_mutex`；不存在反向获取。
  - 序列化在锁外进行（快照后），写盘期间读操作不受影响。
- **无死锁点**：表注册表 `RwLock` 只在建表时短暂持有；不与其他锁嵌套（写锁内不访问注册表）。

### 3.3 内存模型

- 每行存储为 `Arc<T>`（一次分配）；索引只存 `i64` ID，不复制实体。
- 索引值键：`FieldValue` 枚举（`Int/Bool/Time` 无堆分配；`Text` 为键 owned 字符串）。
- 每个索引的 ID 集合是 `BTreeSet<i64>`：插入/删除 `O(log k)`、迭代有序。

## 4. 性能设计与 C# 对照

| 设计点 | C# | Rust | 影响 |
|---|---|---|---|
| 索引值表示 | `object` 装箱 + `ConcurrentDictionary` 哈希 | `FieldValue` 枚举 + `HashMap`/`BTreeMap` | 消除装箱与反射取值开销 |
| 数值/时间范围 | 遍历全部索引键 `O(n)` | `BTreeMap::range` `O(log n + k)` | 10 万行范围查询从毫秒级降到微秒级（视结果集） |
| 字符串前缀 | 遍历全部键 | `BTreeMap::range` 前缀区间 | 前缀查询 `O(log n + k)` |
| ID 集合 | `ConcurrentHashSet`（无序）+ 查询时 `ToHashSet()` | `BTreeSet`（有序、无复制） | 低基数字段插入从 `O(k)` 降到 `O(log k)`；分页顺序稳定 |
| 主键查找 | `ConcurrentDictionary` 查找（返回引用） | `RwLock` 读 + `HashMap` + `Arc` 克隆 | 实测 134 ns/次 |
| 分页 | 反射 `GetValue` + 全量 `OrderBy` + 两次 `Count` | 索引顺序取前 N 条；无索引才排序 | 实测 9 µs/页（10 万行） |
| 持久化 | 每次修改 `Task.Run`；500ms 内直接 return | 后台线程合并写；写前取走脏标记、写后补写 | 写次数大幅下降且**不丢尾写** |
| 字段访问 | 反射 `PropertyInfo.GetValue` | 用户实现 `get_field`（`match`） | 无反射开销（索引键仍需克隆字符串） |

### 4.1 优化过程（本轮实测）

| 阶段 | 插入 10 万行 | `update` 1 万行 | 原因 |
|---|---|---|---|
| 首版（`Vec` + 线性去重） | 2144 ms（21.4 µs/行） | 899 ms（89.9 µs/行） | 低基数字段（`Status` 2 个取值）每次插入/删除扫描 `O(k)` ID 列表 |
| 规则化优化（`normalize` 按值移动、唯一校验合并） | 2078 ms（20.8 µs/行） | 880 ms（88.0 µs/行） | 减少一次字符串克隆，但仍受线性列表限制 |
| **`BTreeSet` ID 集合** | **693~708 ms（6.9~7.1 µs/行）** | **112~113 ms（11.2~11.3 µs/行）** | 插入/删除 `O(log k)`；更新提升 **7.9×**，插入提升 **3.0×** |

> 分页因 `BTreeSet` 迭代开销从 6 µs 变为 9 µs/页（绝对值仍很小），整体收益远大于该回退。

## 5. 实测数据（Release）

### 5.1 热路径（10 万行，10 个普通索引 + 3 个唯一约束）

| 操作 | 实测 | 归一化 | 说明 |
|---|---|---|---|
| 批量插入 | 693~708 ms | **6.9~7.1 µs/行**（13.6~13.8 万行/秒） | 每批 1000 行；含唯一校验、10 个索引写入 |
| `find_by_id` | 13.3~13.6 ms / 10 万次 | **134 ns/次** | 读锁 + 哈希 + `Arc` 克隆 |

| `find_by(Age)` | 2.79~3.68 s / 1 万次 | **279~368 µs/次** | 平均返回 3333 行（含 3333 次 `Arc` 克隆） |
| `find_by_range(Age)` | 721~834 ms / 1000 次 | **721~834 µs/次** | 平均返回 16670 行 |
| `find_by_page`（索引） | 5.2~8.7 ms / 1000 次 | **5~9 µs/页** | 每页 50 行，不排序 |
| `update` | 880 ms → **112~113 ms** / 1 万行 | **11.2~11.3 µs/行** | 含读取、克隆、删除旧索引、重建全部索引 |
| 并发 `find_by_id` | 8 线程 × 10 万次：104~120 ms | **734~767 万次/秒** | 读读并发近线性 |

## 6. 资源占用审计

### 6.1 线程

| 场景 | 线程数 | 行为 |
|---|---|---|
| `MemoryDb::in_memory()` | 0 | 无后台线程 |
| 默认持久化库 | **1**（`pek-rmdb-persist`） | 有脏数据才写；空闲在 `Condvar` 上无限等待 |
| 多实例 | 每实例 1 个 | 通常每进程 1 个实例 |

无定时器、无轮询、无每 tick 线程（区别于 `dhrust::threading::Timer` 的异步模式）。

### 6.2 内存（结构性估算，10 万行 `User` 示例）

- 实体：6 个 `String` + `Vec<String>`（2 项），按平均 30 字节/字符串 ≈ 0.4~0.6 KB/行 → **40~60 MB**；
- 主存储 `HashMap` + `Arc`：≈ 0.1 MB + 1.6 MB；
- 10 个普通索引 × 10 万 ID 项（`BTreeSet`）：按每项 ~24 字节（含节点/指针分摊）≈ **24 MB**；
- 3 个唯一索引（2 个文本键 + 1 个空值跳过）：≈ 7~10 MB；
- 合计约 **75~95 MB / 10 万行**（含测试字符串），与 C# 版“30~50% 内存优化”后的量级相当，且无装箱对象、无反射缓存。

> 说明：未接入分配器统计（`GlobalAlloc` 计数）以避免额外依赖；如需精确值，可在消费方接入 `dhat`/`jemalloc` 统计。

### 6.3 磁盘 IO

- 写盘策略：**全量快照**（与 C# 一致），10 万行 ≈ 20.3 MB/次；
- 合并窗口 500ms：连续写入时最多 2 次/秒；
- 读盘：仅首次访问表时一次；
- 建议：超大表（>100 万行）或高频写入场景应拆表/降低写入频率，或后续引入增量持久化（见 §8）。

## 8. 待办与边界

| 项 | 说明 | 优先级 |
|---|---|---|
| proc-macro 派生 | `#[derive(CacheObject)]` 减少 `get_field/set_field` 样板 | 中 |
| 增量持久化 | 目前全量快照；大表可改为按行 diff（需变更日志/版本号） | 中（>100 万行时） |
| 索引直接持有 `Arc` | `find_by` 结果组装可省一次 `HashMap` 查找（内存 +8/16 字节/索引项） | 低（当前 107 ns/行） |
| 无锁读快照 | 读路径可进一步用 `arc-swap` 全表快照（写少读多极致场景） | 低 |
| 全量排序分页优化 | 索引缺失时用 `select_nth_unstable` 只取目标页 | 低 |
| 读写分离/分片 | 单表单写锁；超高频写入可考虑分片表 | 视消费方需求 |
| P0 观测 | 已有 `statistics()`（行数/索引/写盘次数/字节/耗时） | — |

**明确边界**：
- 本库是**内存数据库**：全量数据常驻内存，不适用于超过可用内存的数据集；
- 单表写操作串行（`RwLock` 写锁），写吞吐上限由唯一校验 + 索引更新决定（约 14 万行/秒/表）；
- 时间字段统一 `NaiveDateTime`（本地时间语义）；跨时区业务需自行换算；
- 文本范围按小写字典序（与 C# `OrdinalIgnoreCase` 在极端 Unicode 场景可能不同）。
