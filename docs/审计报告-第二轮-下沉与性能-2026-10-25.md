# Pek.RMDB 第二轮审计：下沉与性能（2026-10-25）

> 版本：`pek-rmdb 0.1.0`（本轮为增量优化）
> 参照：`G:\Code\Pek.FrameWork\Pek.MDB`
> 方法：全量代码审查 + 依赖/重复实现盘点 + Release 基准实测（`tests/perf_guard.rs`）
> 环境：Windows，Rust 1.99.1，Release（默认 release profile），桌面级 x86_64 CPU

## 1. 结论摘要

| 维度 | 结论 |
|---|---|
| 可下沉能力 | 本轮识别 7 项候选；**4 项已下沉/复用**（原子写、通配匹配、智能布尔、宽松时间 + 数字格式化），3 项评估后不下沉（见 §3） |

| 代码量 | 删除本地重复实现约 200 行（value/json/persistence/index），公共能力统一走 `dhrust` |

## 2. 范围与方法

1. **词法盘点**：扫描 `dhrust` 的 `io`/`text`/`times`/`json` 公共 API，与 Pek.RMDB 本地实现逐项比对（避免“重复造轮子”）。
2. **全量代码审查**：`value/model/index/unique/table/json/persistence/db` 八个模块（锁序、边界、错误路径、分配、热路径）。
3. **性能实测**：`cargo test --release --test perf_guard -- --ignored --nocapture --test-threads=1`，多次运行取区间。
4. **回归**：两仓（DH.RustBase / Pek.RMDB）测试与 clippy。

## 3. 下沉候选矩阵

### 3.1 本轮已下沉/复用

| 候选 | 去向 | 说明 |
|---|---|---|
| 原子写文件（临时文件 + 替换） | `dhrust::io::write_all_text_atomic` | 已有实现；本轮将其内部改为优先 `safe_replace_file`（更强原子性），Pek.RMDB 删除本地 `write_atomic` |
| `*`/`?` 通配匹配 | `dhrust::io::wildcard_match(pattern, text)` | 已有实现；本轮改为**迭代 + 回溯**（避免多 `*` 指数级递归），Pek.RMDB 删除本地版本并复用（`?` 为新增增强） |
| 智能布尔文本 | `dhrust::text::parse_bool` | 新增；`JsonValue::to_bool`、`value_to_bool`、`FieldValue::to_bool` 三处共用（含 `是/否`） |
| 宽松时间解析 + 数字格式化 | `dhrust::times::{parse_datetime_lax, from_unix_timestamp}`、`dhrust::json::format_number` | 新增；覆盖 C# 斜杠日期、Unix 秒/毫秒、C# `double.ToString()` 口径；Pek.RMDB 删除本地实现 |

> 第一轮已下沉：`dhrust::json::{JsonValue, parse_lax, write_quoted}`（C# 兼容宽松 JSON）。

### 3.2 评估后不下沉（含理由）

| 候选 | 理由 |
|---|---|
| `FieldValue` / `FieldKind` / `TimePattern` | 内存数据库的类型系统（索引策略、规范化、时间分组），与业务契约强耦合；dhrust 无同类抽象，强提会引入无消费方的半成品 |
| `PagedResult<T>` | 与 RMDB 查询 API 绑定；各面板分页 JSON 信封不同（`PageIndex/PageSize/TotalCount` vs `page/size/total`），需先统一生态口径；单消费方 |
| `PersistHub`（写合并调度） | 需要 `Weak<表>`/错误回调等业务引用；`dhrust::threading` 的 `Timer` 已覆盖定时场景；抽象为通用原语收益低、间接层多 |
| `table_path`（类型名 → 文件名清洗） | 与 `dhrust::io::safe_file_name` 语义不同（容忍替换 vs 拒绝），且类型名来自代码常量；单消费方 |
| 实体序列化/反序列化（`serialize_snapshot`/`parse_entities`/`coerce_json`） | 依赖 `CacheObject` 字段描述与 `FieldKind`；属于本库持久化契约 |
| `IndexStatistics`/`TableStatistics`/`DbStatistics` | 项目观测模型；字段口径（索引命中率、写盘字节）与面板统计不同 |
| `ops_of`（类型擦除函数指针） | 与 `CacheObject` 绑定的内部实现细节 |

## 4. 性能优化（本轮实施）

| 优化 | 内容 | 收益 |
|---|---|---|
| **更新按字段 diff** | `update` 不再“删全部索引 + 重建全部索引”，而是逐字段比较规范化后的旧/新键，只改动变化项；唯一索引提供两阶段 `update_entity`（先校验全部变更、再统一应用） | `update` **11.2→3.2 µs/行（3.5×）** |
| 索引槽预建 | `IndexSet::new_with_fields` 在建表时按 `fields()` 一次性创建槽；写入走 `get_mut` 快速路径 | 插入小幅改善（-2%，噪声内） |
| 脏标记只在首次唤醒 | `Table::mark_dirty()` 返回“是否 clean→dirty”，连续写入只在第一次唤醒后台线程 | 降低调度锁竞争（写路径少一次 `Mutex` + `notify`） |
| 分页 fallback | 无排序字段：按 ID 整数排序取页；有字段但索引不完整：`select_nth_unstable_by` 只选目标页边界再排序 | 大表无索引分页从 `O(n log n)` 降为 `O(n + k log k)` |
| 结果收集预分配 | `collect_by_ids` 按 ID 数量预分配 `Vec` | 少一次扩容/复制 |
| 多条件按候选集排序 | `find_by_multiple` 先查 `id_count` 最小的条件 | 缩小交集规模 |
| 热路径精确字段名 | `index_entity`/`remove_index_entity` 用 `== "Id"/"Name"` 而非大小写不敏感比较 | 每行少 2 次字符串比较 |

### 4.1 实测数据（Release，10 万行 / 11 个索引）

| 操作 | 本轮优化前 | 本轮优化后 | 变化 |
|---|---|---|---|
| 批量插入 | 6.9~7.1 µs/行 | **6.8~6.9 µs/行**（14.5~14.8 万行/秒） | ≈（-2%） |
| `find_by_id` | 133~142 ns | **120~142 ns** | ≈（噪声） |
| `find_by_unique` | 429~433 ns | **429~436 ns** | ≈ |
| `find_by(Age)`（3333 行） | 279~368 µs | **362~369 µs** | ≈ |
| `find_by_range`（16670 行） | 721~834 µs | **834~861 µs** | ≈ |
| `find_by_page`（索引） | 5~9 µs | **8~9 µs** | ≈ |
| `find_by_page`（无索引字段，10 万行） | 未测 | **19.8 ms/次**（首次基线） | — |
| `find_by_page`（无排序字段） | 未测 | **1.35 ms/次**（首次基线） | — |
| **`update`** | **11.2~11.3 µs/行** | **3.05~3.23 µs/行** | **3.5× 提升** |
| 并发 `find_by_id`（8 线程） | 734~767 万次/秒 | **668~740 万次/秒** | ≈（噪声） |
| 全量写盘（10 万行） | 127.5 ms / 20.3 MB | **126~128 ms / 20.3 MB** | ≈ |
| 原子写残留 | 0 | 0（改用 dhrust 统一实现后仍为 0） | — |

> 波动说明：桌面机负载/散热导致读路径 ±5~10% 抖动；`update` 的 3.5× 为稳定可复现收益（多轮一致）。

### 4.2 未实施（评估结论）

| 候选 | 评估 |
|---|---|
| 索引直接持有 `Arc` | 可省 `find_by` 结果组装的一次哈希查找（约 -18%），但每个索引项 +8 字节（10 万×11 ≈ 8.8 MB）且更新需维护 Arc 一致性；性价比低 |
| `parking_lot::RwLock` | 读锁在 Windows 已为 SRWLOCK，收益小；引入新依赖违背“最小依赖” |
| 文本索引去掉双份（exact + lower） | 需要额外结构保存原值或改为大小写敏感查询；与 C# 行为对齐优先，暂不优化 |
| 压缩持久化（gzip） | 可减小写盘/带宽约 75%，但破坏与 C# 的纯 JSON 互通；如需可作为可选 feature |
| 增量持久化（按行 diff） | 大表（>100 万行）收益显著，需变更日志/版本号，列入待办 |

## 5. 全量审计

### 5.1 正确性

| 检查项 | 结果 |
|---|---|
| 唯一约束失败不改变状态 | ✅ `validate` 与 `update_entity` 均两阶段；冲突测试通过 |
| 更新按字段 diff 的索引一致性 | ✅ 旧值删除/新值建立仅针对变化字段；`update_excludes_self_but_detects_others` 等测试通过 |
| 复合唯一键 diff | ✅ `composite_key_opt` 统一空值语义；测试通过 |
| Name 变化时索引更新 | ✅ 单独 diff（含空名） |
| 唯一竞争并发 | ✅ 8 线程抢同一唯一值仅 1 个成功 |
| 加载时 ID 计数器/唯一冲突 | ✅ 保持第一轮修复 |
| C# 文件兼容 | ✅ 裸键/注释/斜杠日期/尾逗号；时间解析改走 dhrust（行为保持一致，测试覆盖） |

### 5.2 并发与锁

- 读：`RwLock` 读锁 + `HashMap`/索引只读；8 线程 740 万次/秒。
- 写：`RwLock` 写锁内完成「校验 → 索引 diff → 主存储替换」；无嵌套锁。
- 持久化：后台线程快照（克隆 `Arc`）→ 锁外序列化 → `save_mutex` 内写盘；写前“取走”脏标记（不丢尾写）。
- `mark_dirty` 改为 `swap(true)`，返回是否首次置脏；后台唤醒由 db 层统一处理（无重复通知）。

### 5.3 资源

| 项 | 数值 |
|---|---|
| 线程 | 1 个（`pek-rmdb-persist`），空闲 `Condvar` 等待（零轮询） |
| 内存（10 万行 `User`，结构性估算） | 75~95 MB（实体 40~60 MB + 索引约 24 MB + 唯一索引 7~10 MB） |
| 写盘 | 20.3 MB / 次（10 万行），500ms 合并；空闲 0 IO |
| 单次 `update` 索引写操作 | 典型 1~2 个字段（原为全部 11 个索引） |

### 5.4 依赖

- `chrono` + `dhrust`（`times`/`json`/`io`/`text`）；无 serde、无异步运行时、无第三方数据结构/锁库。
- 本轮新增复用：`io::write_all_text_atomic`、`io::wildcard_match`、`text::parse_bool`、`times::{parse_datetime_lax, from_unix_timestamp}`、`json::format_number`。

## 6. 待办

1. proc-macro 派生（减少 `get_field/set_field` 样板）。
2. 增量持久化（按行 diff / 变更日志），适配 >100 万行。
3. 无索引排序字段分页的键提取优化（当前 19.8 ms/10 万行；可通过实体提供借用键避免 `String` 克隆）。
4. 统一生态分页/统计模型的评估（若面板类项目出现第二消费方，再下沉 `PagedResult`）。
5. 可选：压缩持久化（feature，需明确放弃 C# 互通时才启用）。
