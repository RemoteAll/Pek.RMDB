| 方向 | 结论 |

## 2. 第三轮下沉（4 项）

### 2.1 `dhrust::web::Paged<T>`

```rust
pub struct Paged<T> { pub items: Vec<T>, pub page_index: usize, pub page_size: usize,
                      pub total_count: usize, pub total_pages: usize }
impl<T> Paged<T> { pub fn new(items, page_index, page_size, total_count) -> Self; pub fn is_empty(&self) -> bool }
```

- 取代 RMDB 本地 `PagedResult`（保留 `pub use dhrust::web::Paged as PagedResult;` 兼容旧导入）。
- `page_size.max(1)` + `div_ceil` 口径随迁，RMDB 旧结构字段完全一致，调用方零改动。
- 生态内其它分页界面（RAdmin / RAgent 面板）可复用，避免每仓再写一遍分页信封。

### 2.2 `dhrust::times::date_range_of(pattern) -> Option<(NaiveDateTime, NaiveDateTime)>`

- 输入 `"2024"` / `"2024-01"` / `"2024-01-05"`（含 `2024/01` 口径），输出**日精度闭区间**；
- 取代 RMDB 本地 `TimePattern` 枚举与其 `time_pattern_ranges` 测试（值解析仍在 `value.rs`）。
- 与 `parse_datetime` / `parse_datetime_lax` 同源（都基于 chrono），时区/边界口径一致。

### 2.3 `dhrust::io::sanitize_file_name(raw) -> String`

- 非法字符（Windows 保留字符 + 路径分隔符）、控制字符 → `_`；`..` → `__`；空串 → `_`；
- 用途：把**业务类型名**安全映射为数据文件名（RMDB `Data/{type_name}.json` 的路径穿越护栏），
  以及日志/导出文件名等通用场景。

### 2.4 `dhrust::io::exe_dir() -> PathBuf`

- 程序所在目录（Windows 取 `current_exe` 父目录，失败回退当前目录）；
- 取代 RMDB `default_base_dir()` 里的本地实现；`io::base_dir(env_names)` 已有环境变量覆盖语义，两者互补。

### 2.5 不下沉复核（明确保留在 RMDB）

| 候选 | 理由 |
|---|---|
| `PersistHub`（Condvar + 最小间隔合并写盘） | 与"内存表 + 脏标记"的数据模型强耦合；通用化成 `dhrust::persist` 需要定义快照/序列化契约，收益不足以覆盖抽象成本 |
| `FieldValue` / `FieldKind` | C# `Pek.MDB` 口径的值模型（含 `Time`/`List`/`Map` 与规范化规则），属本库契约 |
| `Table` / `IndexSet` / `UniqueSet` | 存储核心（整表 `RwLock` + `BTreeSet` 索引 + 两阶段唯一约束），无可复用边界 |
| `serialize_snapshot` / `parse_entities` | C# `SimpleJsonString` 裸键格式，与 `dhrust::json` 的"通用宽松解析"职责不同 |
| 统计结构（`IndexStatistics`/`TableStatistics`/`DbStatistics`） | 本库专属观测模型 |
| `insert` 合并 `get_field` 次数（11→8） | 需改 `UniqueSet`/`IndexSet` 的入参契约，实测收益 <3%，风险大于收益 |

## 3. 性能优化：FxHash 容器

### 3.1 动机

标准库 `HashMap` 默认 `SipHash-1-3`（抗 HashDoS）。内存数据库的键全部来自**类型化业务实体**，
不存在不可信外部输入；而一次插入/查询要发生 10+ 次哈希查找。改用 FxHash 后单次哈希从 ~20 ns 降到 1~3 ns。

### 3.2 实现

`src/hash.rs`：`FxHasher`（`rotate_left(5) ^ value` 后乘 `0x517cc1b727220a95`，实现
`write/write_u8/u16/u32/u64/usize`，`&[u8]` 走 `as_chunks::<8>` 尾块补零）+
`FastMap<K,V>` / `FastSet<T>` 别名 + `new_map()`。

**替换点（6 处）**：

| 位置 | 原类型 | 说明 |
|---|---|---|
| `table.rs::State.by_id` | `HashMap<i64, Erased>` | 所有读路径的最后一跳，收益最大 |
| `table.rs::find_by_multiple` | `HashSet<i64>` | 多条件交集 |
| `unique.rs::UniqueSet.fields/composites` | 两层 `HashMap` | 唯一约束校验（每次写入必经） |
| `index.rs::IndexSet.slots` | `HashMap<&'static str, IndexSlot>` | 每个字段索引的定位 |
| `index.rs::TypedIndex::Exact` | `HashMap<FieldValue, BTreeSet<i64>>` | JSON 值索引 |
| `index.rs::TextIndex.exact` | `HashMap<String, BTreeSet<i64>>` | 文本精确索引 |

保留 `BTreeMap`/`BTreeSet` 用于**范围查询与有序遍历**（哈希无法替代）。

### 3.3 实测（Release，10 万行 / 11 索引 / 3 唯一，`--test-threads=1`）

| 指标 | 第二轮 | 第三轮 | 变化 |
|---|---|---|---|
| 插入 | 6.8~6.9 µs/行 | 6.81 µs/行（146,771 行/秒） | 持平 |
| `find_by_id` | 120~142 ns | **107 ns** | **-15%** |
| `find_by_unique` | 429~436 ns | **393 ns** | **-9%** |
| `find_by(Age)`（返 3333 行） | 362~369 µs | **163.7 µs** | **-55%** |
| `find_by_range`（返 16670 行） | 834~861 µs | **410.3 µs** | **-51%** |
| `update` | 3.05~3.23 µs/行 | 3.07 µs/行 | 持平 |
| `find_by_page`（索引顺序） | 8~9 µs | **7 µs** | -12~22% |
| `find_by_page`（无索引字段） | 19.8 ms | 20.3 ms | 噪声内 |
| `find_by_page`（无排序） | 1.35 ms | 1.32 ms | 基本持平 |
| 并发 `find_by_id` 8 线程 | 668~740 万次/秒 | **817 万次/秒** | **+10~22%** |
| 全量写盘 | 126~128 ms | 124.5 ms（20.30 MB） | 基本持平 |

**为什么低基数/范围查询提升巨大**：两者都把结果 ID 逐个回 `by_id` 取对象（3333 / 16670 次），
`find_by_id` 单点的 -15% 被放大成 2 倍级整体收益。插入/update 的瓶颈在唯一约束与 `BTreeSet`
索引维护（`O(log k)` 插入 + 两阶段校验），与哈希实现无关，符合预期。

### 3.4 写盘容量估算

`serialize_snapshot` 的初始容量由 `items.len() * 96 + 4` 调整为 `* 192 + 64`：
实测 10 万行 20.3 MB ≈ 213 B/行（含 11 索引字段的实体），原估算触发 1~2 次整串扩容
（20 MB 级拷贝）。调整后大快照少一次倍增拷贝，小表多占几百字节可忽略。

### 3.5 权衡与风险

- **抗碰撞**：FxHash 不抗 HashDoS。本库键来自可信实体；若未来引入"公网直传字段名/键值"，
  应改回 `RandomState` 或对入参做白名单校验（已在 `hash.rs` 模块文档写明）。
- **不改变语义**：仅换 `BuildHasher`，`HashMap` 的迭代顺序本就未定义，代码中无依赖迭代顺序的逻辑
  （已检查：`statistics`/`find_all` 均按 ID 或索引顺序输出）。

## 4. 全量审计

### 4.1 正确性

| 项 | 结论 |
|---|---|
| C# 双向兼容 | `Data/{type_name}.json` 裸键 + `\r\n`/`\t` + `Id`/`Name` 前置；读容忍注释、尾逗号、斜杠日期、带引号键；本轮未改格式（3 项 json 测试 + 11 项持久化测试覆盖） |
| 唯一约束 | 两阶段（先全量校验、再统一落索引），失败不改任何状态；`update_entity` 按字段/复合 diff；加载冲突**跳过对象**而非留下不一致状态 |
| ID 计数器 | 加载后修正为 `max(id)+1`（C# 未修正，属已知缺陷修正） |
| 索引值规范化 | 全部按 `FieldKind` 规范化后再入索引，`i32`/`i64` 跨类型查询命中 |
| 分页 | `Paged` 字段语义与 RMDB 旧结构一致（`page_size.max(1)`、`total_pages = div_ceil`），7 项分页测试覆盖 |

### 4.2 并发

- 整表 `RwLock<State>`：读只取读锁、写单写者；`dirty: AtomicBool` 做写盘唤醒去重（`swap(true)` 只有首次为真）。
- 后台线程**唯一**：`PersistHub` 的 Condvar 等待，无脏数据时无限等待（零轮询、零 CPU）。
- 本轮无新增线程、无新增锁；`FastMap` 与 `HashMap` 在 `RwLock` 内的访问模式完全相同。
- 并发测试 4 项（多线程读、读写混合、flush 竞争、Drop 收尾）全绿。

### 4.3 资源

- 依赖：`chrono` + `dhrust`（dev: `tempfile`）；FxHash 为**自实现 60 行**，未新增依赖。
- 内存：`FastMap` 与 `HashMap` 布局相同（哈希值 + 键值对），无额外开销；
  `by_id` 存 `Arc` 快照，读返回克隆（引用计数），不复制实体。
- 磁盘 IO：写盘按 500 ms 合并、原子替换（`safe_replace_file`），10 万行 20.3 MB 一次写。
- 周期行为：后台线程无常驻定时器，符合"变化驱动、无变化零劳作"口径。

## 5. 剩余待办（评估后暂不做）

| 项 | 评估 |
|---|---|
| 无索引字段排序分页 20.3 ms / 10 万行 | 每次调用都要全表取键 + 部分选择；加缓存需处理"字段变更即失效"，复杂度高。建议调用方为排序列建索引（`Field::int` 默认索引） |
| 增量持久化（>100 万行只写变化行） | C# 格式是**整表单文件**，增量写会破坏双向兼容；需另立 sidecar 格式，待真实需求 |
| 持久化压缩 | 同上：文件要能被 C# 直接读，压缩只能做旁路 `.zst`，收益与兼容成本需再评估 |
| `proc-macro` 派生 `CacheObject` | 手写 `const fn` 字段表已足够短（约 10 行/实体），引入 proc-macro 依赖会拖慢全生态编译 |
| 插入合并 `get_field`（11→8 次） | 实测收益 <3%，需改内部契约，不做 |
